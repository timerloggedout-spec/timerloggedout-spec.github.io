Explore the work and its evidence

How to explore the work and its evidence

This site is the orientation layer for a human-directed software and research fleet. It connects public repositories, operational dashboards, project applications, and the evidence that explains how each result was produced. Use the project hub as the broad index, then open the focused surface that answers your question. Each surface has a distinct purpose, and each status view points back toward its source record.

Start with the right project surface

The project hub introduces the development and management repository, its architecture, and its working lanes. Tribute presents operational evidence, repository activity, generated receipts, and control-surface views. LANE-MATRIX summarizes pull-request lanes, assignment reasons, and elapsed time. These dashboards are separate views of the same project ecosystem, with their own source contracts and update paths.

StudySprint turns a verified syllabus into a study plan, recall practice, and a re-planning workflow. Delphi Oracle evaluates evidence gates and returns a decision with a versioned receipt. Repo+Story turns repository history into cited change narratives. Follow the source links on each project page to inspect implementation details, test records, and the repository history behind the visible experience.

Read evidence before reading a status label

A dashboard value is a projection of a source record. For delivery work, the strongest evidence is the repository commit, pull request, review, workflow run, and deployed artifact. For an oracle decision, inspect the evidence inputs, policy version, decision state, and receipt. For a study plan, inspect the source syllabus, verification receipt, plan version, and re-planning history. Each claim should lead to a record that a reader can open and evaluate.

Freshness is part of the evidence. A generated feed should identify its generation time and source window. A stale feed should carry a stale state, and a missing feed should remain an observable gap. Read timestamps, source links, and version identifiers together. A status label without a source receipt is a summary; a status label with a receipt is an auditable statement that can be checked against its origin.

Follow a change from proposal to publication

Work begins with a scoped proposal or issue. The proposal records the intended outcome, constraints, owners, acceptance checks, and review path. Implementation happens on a focused branch, with tests and repository checks attached to the change. A pull request exposes the diff and review discussion. A successful merge records the resulting commit. A publication workflow then transfers source-owned artifacts to the public site, where the deployed page can be checked independently.

Keep these stages distinct when interpreting progress. A queued workflow is pending evidence. A passing test validates the tested scope. A merged pull request proves that the change entered the target branch. A successful deployment run proves that publication executed. A live scan proves that the current public response exposes the expected content. The full chain gives readers a useful trail from intent to implementation to publication.

Understand the human-directed agent model

AI collaborators support research, planning, implementation, review, and operational analysis under human direction. Each task has a scope, an authorized action set, and a verification path. Agent names and display monikers help readers understand attribution; the actual repository, provider, model, adapter, and execution role remain separate facts. Routing follows registered tools and permissions, while project records preserve the evidence needed to explain each action.

Automation should make progress observable and reversible. Prefer bounded work, explicit acceptance checks, isolated branches, and receipts that identify the changed files and commit. Escalate when a task reaches a credential boundary, a destructive operation, a production setting, or a decision that requires human authority. This model keeps the work moving while making responsibility and provenance clear.

Use the open retrieval formats

The site publishes llms.txt as the concise entry index and llms-full.txt as the expanded project context. The Markdown sitemap groups the public routes, and each supported HTML page links to a sibling Markdown representation. The project glossary defines shared terms. These files give readers and AI agents stable, text-first paths into the site.

HTML and Markdown are parallel representations of the same public information. GitHub Pages serves the static files and alternate links. Per-response HTTP Link headers and Accept-based Markdown negotiation require a programmable edge or application server, so the static Markdown routes remain the reliable fallback. Public pages use visible canonical text; experimental internal encodings belong in separate research artifacts with a readable sidecar and decoder.

Interpret the Agent Readability badge carefully

The Agent Readability badge is reserved for a fresh, verified score of 95/100 or higher. Its status record must include the scan URL and verification timestamp. The badge stays hidden while the score is unknown or below the threshold. Open the linked scan to inspect the checks and the page set behind the score; treat the score as a dated measurement rather than a permanent property of the site.
