Repo+Story · concept of record · Idea I1

Read the story of what changed.

Repo+Story is a PR/repo-history narrative for review & maintenance. It ingests a repository's git event-stream — commits × file mutations × authors, the data Gource consumes, not its animation — and produces a clustered, blast-radius-aware story in which every claim is cited back to its source commit. Reviewers and maintainers read what changed, why it matters, and what it touches — instead of re-deriving it from raw history.

View the repo Concept of record The Spec

The problem

Repo history is write-only memory: commits, PRs and file mutations accumulate, but the story — what changed together, what it put at risk, who touched it — must be re-derived by every reviewer and maintainer, every time.

How the story gets built

A chronological evolution, not a static diff — narrated by a “technical code chronicler”, with strict markdown citations: [Description](commit_hash).

STEP 1 · INGEST

The event-stream

Commits × file mutations × authors — the Gource data plane, not its animation.

STEP 2 · CLUSTER

Story units

Events grouped by change coupling, file neighborhoods, authorship, and time windows — past a noise filter (lockfiles, linters), with rename lineage kept.

STEP 3 · BLAST RADIUS

The risk footprint

Each unit carries its touched-surface footprint: co-changing file clusters are implicit dependencies, made explicit.

STEP 4 · NARRATE

Every claim cited

The story is generated with every claim cited ↦ its source commit. An uncited claim does not ship.

STEP 5 · PUBLISH

Sticky story

A GitHub Action posts and updates a sticky story on the PR.

git history→ PyDriller extraction (Python)→ clustering + blast-radius→ cited narrative→ GitHub Action sticky comment

Concrete artifacts in the spec: extract_pr_story_context and mine_pr_evolution (file-coupling matrix; payload {metadata, chronological_stream, architectural_coupling}) · workflow .github/workflows/pr_storyteller.yml. The narrative model reads the Iteration Path (change → rewrite → revert = an architectural dead-end story) and the Why-behind-What (commit messages × line diffs = an auditable trail).

Features

🎯

Impact Areas

Alerts on the surfaces a change actually puts at risk — drawn from the coupling and blast-radius analysis, not the diff alone.

🧾

Changelogs with Receipts

Automated changelogs where every line carries its receipt: a citation back to the source commit.

🔍

Contextual Blame

Blame with the story attached — not just who touched a line, but the change narrative it belongs to.

⚠️

Blast-radius maintenance warning

A file changed without its coupled test file — e.g. routes/user.py changed without tests/test_user.py — raises a warning before human review.

Surfaces & persistence

⚙️

GitHub Action

pr_storyteller.yml on pull_request: [opened, synchronize] — posts the story as the sticky first PR comment.

🪝

Pre-push hook

A lightweight local run that produces a draft PR description before the push lands.

📌

Pinned Story

The pinned markdown Story on the PR thread — the durable, readable record of the change.

Persistence is decided in Spec v2: the hybrid is the adopted target — merge → Action → central datastore → coupling alerts → pinned Story — and v0 sequencing starts with M1, the .story/ orphan-ref store. The I1 candidate set is the record the decision was drawn from: .story/ PR-{id}.json (git-native, orphan refs/notes) · a ChromaDB local vector index (.story_vector_db) · a SQL chrono-graph (Commits / FileMutations / Coupling tables, with a shared_commit_count smell flag). One primary store — the set is options, not a commitment to all three.
